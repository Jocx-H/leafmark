# LeafMark 跨平台 Markdown 文档命名管理器设计文档

> 文档状态：设计基线 1.2  
> 产品名称：LeafMark  
> 英文定位：A focused, cross-platform naming manager for Markdown files.  
> 目标读者：产品设计 Agent、开发 Agent、测试 Agent  
> 本文用途：作为后续实现、任务拆分和验收的统一依据

## 1. 项目概述

LeafMark 是一个独立、功能聚焦的 Markdown 文档命名管理器。名称中的 “Leaf” 表示树形分类中的文档叶节点，“Mark” 同时表示 Markdown 以及施加于文件名的编号和标签。LeafMark 不承担 Markdown 阅读或编辑，而是扫描用户指定目录，从文件名中解析编号、标签和标题，并通过图形界面完成规范化命名、分类调整和标签管理。

软件应可分别运行在 Windows 和 macOS 上。这里的“跨设备”仅表示同一软件可以安装并运行在不同操作系统的设备上，不表示软件负责 Markdown 文件的跨设备同步。文件同步由用户自行选择 OneDrive、iCloud Drive、Git、Syncthing 等外部方案完成。

## 2. 已确定的设计决策

以下内容属于项目基线，开发过程中不应在未确认的情况下改变：

1. 产品正式名称为 **LeafMark**，软件定位为外部命名管理工具，不内置 Markdown 编辑器或阅读器。
2. 软件不负责文件云同步，也不提供账号和服务器。
3. 文档元数据的权威来源是 Markdown 文件名。
4. 不使用数据库，不维护需要迁移的文件索引。
5. 允许在管理目录中保存一个非索引型 JSON 配置文件，用于分类名称、固定标签和扫描规则。
6. 六位编号表示文档当前的树形分类位置，不是永久且不可变的文档 ID。
7. 调整分类会修改编号并重命名文件。
8. 软件使用同一套源码，分别构建 Windows 和 macOS 安装包或可执行程序；不存在一个能够同时在两个系统上运行的通用可执行文件。
9. 桌面端技术栈固定为 Electron + Node.js + TypeScript + React，不使用 Rust，也不采用 Tauri + Node.js sidecar。
10. Main Process 是文件操作和最终规则校验的唯一权威；Renderer 不得直接获得 Node.js 或文件系统能力。

## 3. 产品目标与非目标

### 3.1 产品目标

- 让大量 Markdown 文件采用统一、可读、可排序的命名形式。
- 通过六位编号提供两级分类和一级文档序号形成的树形组织。
- 通过一个或多个标签提供跨分类的扁平化检索。
- 允许用户在 Typora、VS Code、文件管理器等外部工具中直接看到文档分类和相邻文档。
- 不绑定任何 Markdown 编辑器，整理完成后可以立即关闭。
- 在 Windows 和 macOS 上保持相同的解析结果和主要交互。
- 即使软件不可用，用户仍能直接理解、打开和手工管理文件。

### 3.2 非目标

第一阶段不实现以下能力：

- Markdown 正文编辑、预览或渲染；
- 全文搜索；
- 云同步、账号系统或多人协作；
- Git 版本管理；
- 附件和图片管理；
- 知识图谱和双向链接系统；
- 数据库或长期文件索引；
- 自动理解文章内容并生成分类；
- 永久删除文件。

## 4. 核心概念

### 4.1 工作区

工作区是用户选择的一个本地目录。软件只管理该目录扫描范围内的 Markdown 文件。

每个工作区可以包含一个 `.leafmark.json` 配置文件。配置文件可以随 Markdown 目录一起被外部同步工具同步，但它不保存文件列表、绝对路径或扫描缓存。

软件可以在操作系统的应用数据目录中记住最近打开的工作区路径。该本机设置不属于工作区配置，也不要求跨设备同步。

### 4.2 管理文档

符合规范命名的 Markdown 文件称为“已管理文档”。其逻辑数据模型如下：

```text
ManagedDocument
├── relativePath      相对于工作区根目录的路径
├── filename          当前文件名
├── code              六位编号 AABBCC
├── primaryCode       一级分类编号 AA
├── secondaryCode     二级分类编号 BB
├── sequenceCode      文档序号 CC
├── tags[]            有序且不重复的标签列表
├── title             文档标题
├── extension         .md
└── status            valid / unmanaged / invalid / conflict
```

这些字段均由当前文件系统状态和文件名即时产生，不持久化为索引。

### 4.3 文档状态

扫描结果中的 Markdown 文件分为四种状态：

| 状态 | 含义 | 允许的主要操作 |
| --- | --- | --- |
| `valid` | 完全符合命名规范，且编号无冲突 | 重命名、调整分类、修改标签 |
| `unmanaged` | 普通 Markdown 文件，尚未使用规范命名 | 纳入管理 |
| `invalid` | 看起来采用了规范，但编号、标签或标题不合法 | 修复命名 |
| `conflict` | 两个或多个文件使用相同六位编号 | 重新分配编号 |

软件不得因文件名不规范而忽略文件。异常文件应当可见，并给出具体原因。

## 5. 六位编号与树形分类

### 5.1 编号结构

编号固定为六位十进制数字：

```text
AABBCC
```

| 字段 | 范围 | 含义 |
| --- | --- | --- |
| `AA` | `00`～`99` | 一级分类 |
| `BB` | `00`～`99` | 一级分类下的二级分类 |
| `CC` | `00`～`99` | 二级分类下的文档序号 |

因此，编号空间理论上包含 1,000,000 个位置；每个二级分类最多包含 100 个编号位置。

`00` 是合法值。默认配置可以把一级分类 `00` 和二级分类 `00` 显示为“未分类”，但用户可以修改其展示名称。编号 `000000` 也是合法编号。

### 5.2 编号语义

编号表示文档当前的分类位置：

```text
010203
```

表示一级分类 `01`、二级分类 `02` 下序号为 `03` 的文档。

移动文档到其他分类时，软件需要生成新编号并重命名文件。例如：

```text
010203_[CUDA]_稀疏内核.md
        ↓ 移入 03/01 分类
030104_[CUDA]_稀疏内核.md
```

编号不是独立于文件名保存的永久标识。文件重命名后，旧编号不再代表该文档。

### 5.3 唯一性范围

六位编号在整个工作区扫描范围内必须唯一，而不是只在同一个物理子目录内唯一。若不同子目录出现相同编号，二者都标记为 `conflict`。

### 5.4 自动分配规则

创建文档、纳入管理或移动分类时，软件自动推荐目标二级分类中的下一个编号：

1. 获取同一 `AA/BB` 下所有有效的 `CC`；
2. 优先推荐“当前最大值 + 1”；
3. 不主动填补中间空缺，避免用户删除文档后立即复用旧编号；
4. 当最大值为 `99` 时，不自动复用空缺，提示用户手工选择空闲编号；
5. 用户可以覆盖推荐值，但提交前必须通过合法性和冲突检查；
6. 若 `00～99` 已全部占用，则该二级分类已满，必须选择其他二级分类。

因为项目不保存历史索引，软件无法永久保证已删除编号永不复用。第一阶段只保证不会自动填补中间空缺。

## 6. 文件名规范

### 6.1 标准格式

带标签文件：

```text
AABBCC_[标签1][标签2]_文章标题.md
```

示例：

```text
010203_[CUDA][SpMM]_稀疏矩阵乘优化.md
```

无标签文件：

```text
AABBCC_文章标题.md
```

示例：

```text
010204_实验环境记录.md
```

文件名由以下部分构成：

1. 恰好六位数字编号；
2. 一个半角下划线 `_`；
3. 可选的连续标签块；
4. 标签块存在时，再使用一个半角下划线 `_` 与标题分隔；
5. 非空标题；
6. 小写扩展名 `.md`。

标题内部允许包含下划线。解析器只把编号后的标签前缀识别为标签区域，其余内容均属于标题。

### 6.2 解析规则

解析必须按步骤执行，不应只使用一个大正则表达式，以便给出准确错误信息：

1. 检查扩展名是否为 `.md`，扫描时扩展名匹配不区分大小写；
2. 读取开头六个字符并验证均为 ASCII 数字；
3. 验证编号后存在 `_`；
4. 若剩余部分以 `[` 开头，则连续解析一个或多个 `[标签]`；
5. 标签块后必须存在 `_`；
6. 将剩余部分解析为标题；
7. 对编号唯一性、标签、标题和最终文件名进行二次校验。

为消除无标签文件的歧义，无标签标题不能以 `[` 开头。若用户确实需要以方括号开头的标题，应将方括号中的内容作为标签，或修改标题表达。

### 6.3 标签规范

- 一个文件可以包含零个或多个标签；
- 标签顺序由用户决定并保留，界面允许调整顺序；
- 同一文件内的标签不得重复；
- 标签身份比较默认不区分拉丁字母大小写，显示形式保留第一次扫描到或用户选定的写法；
- 标签在比较和写入前统一转换为 Unicode NFC；
- 自动移除标签首尾空白；
- 标签不能为空；
- 单个标签建议不超过 20 个 Unicode 字符；
- 标签不得包含 `[`、`]`、换行符、控制字符或 Windows 禁止字符 `< > : " / \\ | ? *`；
- 标签不得以空格或句点结尾。

修改标签本质上是一次文件重命名。软件不在 Markdown 正文或 Front Matter 中写入标签。

### 6.4 标题规范

- 标题不能为空；
- 自动移除首尾空白；
- 标题在写入前统一转换为 Unicode NFC；
- 标题不得包含换行符、控制字符或 `< > : " / \\ | ? *`；
- 标题不得以空格或句点结尾；
- 标题允许包含中文、英文、数字、空格、圆括号、方括号和下划线，但无标签标题不能以 `[` 开头；
- 软件不应擅自替换标题中的内部空格或标点。

### 6.5 跨平台长度限制

为了兼容 Windows、macOS 和常见同步工具，最终文件名应满足：

- UTF-8 编码后不超过 200 字节；
- 当前系统中的完整路径通过运行时合法性检查；
- 目标路径不得与已有文件发生区分大小写后的冲突；
- Windows 上禁止尾部空格和尾部句点。

若超过限制，界面必须显示当前长度和允许长度，而不是静默截断标题。

## 7. 标签来源与生命周期

工作区中的可用标签集合由两部分组成：

```text
可用标签 = 文件名扫描所得标签 ∪ 配置文件中的 pinnedTags
```

- 用户可以在创建、纳入管理或重命名文档时输入新标签；
- 新标签随重命名成功后进入扫描所得标签集合；
- 当最后一个使用某标签的文件被删除或改名后，该标签会从扫描集合中消失；
- 如果该标签位于 `pinnedTags`，即使暂时没有文档使用，也继续出现在候选列表中；
- 删除标签不是独立修改文档内容的操作，而是从相关文件名中移除标签；
- 标签筛选使用“包含全部所选标签”和“包含任一所选标签”两种模式。

## 8. 工作区配置文件

### 8.1 文件位置与性质

配置文件固定为工作区根目录下的：

```text
.leafmark.json
```

它是非索引型配置，只保存规则和展示信息。禁止在其中保存：

- 扫描得到的文件列表；
- 文档到编号的映射；
- 文件绝对路径；
- 文件修改时间缓存；
- 用于恢复文档身份的内部 ID。

删除配置文件不会导致 Markdown 文件元数据丢失；软件应使用默认配置重新解析文件名。

### 8.2 建议结构

```json
{
  "schemaVersion": 1,
  "scan": {
    "recursive": true,
    "extensions": [".md"],
    "followSymlinks": false,
    "ignoreGlobs": [
      ".git/**",
      "node_modules/**",
      "attachments/**"
    ]
  },
  "categories": {
    "00": {
      "name": "未分类",
      "children": {
        "00": "未分类"
      }
    },
    "01": {
      "name": "科研",
      "children": {
        "01": "论文阅读",
        "02": "实验记录"
      }
    }
  },
  "pinnedTags": [
    "CUDA",
    "SpMM",
    "LLM"
  ],
  "behavior": {
    "confirmBeforeRename": true,
    "warnAboutLinks": true
  }
}
```

### 8.3 配置校验

- `schemaVersion` 必须存在；
- 一级和二级分类键必须是两位数字；
- 分类展示名称不能为空；
- `pinnedTags` 使用与普通标签相同的校验规则；
- 忽略规则相对于工作区根目录解释；
- 未知字段应被保留或忽略，不应导致整个工作区无法打开；
- 配置损坏时进入只读扫描状态，显示错误位置，并允许用户恢复默认配置或重新选择目录；
- 写入配置时采用“临时文件 + 原子替换”，避免程序异常中断留下半个 JSON 文件。

## 9. 扫描、监听与刷新

### 9.1 初次初始化

用户首次打开软件时：

1. 选择一个工作区目录；
2. 软件验证目录可读取；
3. 读取或创建 `.leafmark.json`；
4. 按配置扫描 Markdown 文件；
5. 解析文件名并检查编号冲突；
6. 汇总分类、标签和异常；
7. 显示工作区主界面。

创建默认配置文件前应向用户说明；若用户选择“不创建”，软件仍可以使用内存默认配置运行。

### 9.2 扫描规则

- 默认递归扫描；
- 扩展名匹配不区分大小写，但规范化重命名统一写为 `.md`；
- 默认不跟随符号链接；
- 忽略 `.git`、`node_modules` 和配置中指定的路径；
- 目录无权限、文件名解码失败等问题应汇总展示，不得导致整个扫描失败；
- 只读取目录项和文件元数据，第一阶段不读取 Markdown 正文。

### 9.3 运行时更新

不应在每次界面操作后阻塞式全量扫描。推荐机制：

1. 启动或切换工作区时全量扫描；
2. 软件自身成功重命名后立即更新内存视图；
3. 使用文件系统监听器感知外部新增、删除和重命名；
4. 对连续事件进行约 300～500 ms 防抖；
5. 监听事件无法可靠解释时执行后台全量校验；
6. 提供明确的“重新扫描”按钮。

内存数据只是当前界面状态，不是持久化索引。重新启动后必须从文件系统重新构建。

## 10. 用户界面设计

### 10.1 主界面布局

推荐采用三栏布局：

| 区域 | 内容 |
| --- | --- |
| 左侧 | 一级分类、二级分类和文档数量组成的树 |
| 中间 | 当前分类下的文档列表、搜索和标签筛选 |
| 右侧 | 所选文档的编号、分类、序号、标签、标题和校验结果 |

顶部工具栏包含：

- 当前工作区名称和路径；
- 切换工作区；
- 新建 Markdown 文件；
- 将未管理文件纳入规范；
- 重新扫描；
- 设置。

### 10.2 文档列表

列表默认按六位编号升序排列，并至少显示：

- 六位编号；
- 标题；
- 标签；
- 相对目录；
- 当前状态。

支持按标题和文件名进行即时筛选，但不搜索正文。

### 10.3 编辑面板

编辑面板允许：

- 选择一级分类；
- 选择二级分类；
- 查看或修改两位文档序号；
- 添加、移除和调整标签顺序；
- 修改标题；
- 实时查看目标文件名；
- 查看所有校验错误和警告；
- 提交重命名或取消修改。

用户改变分类时，软件应立即推荐目标分类的下一个序号，但在用户确认前不得修改文件。

### 10.4 未管理与异常文件

界面提供独立筛选入口：

- “未纳入管理”；
- “命名异常”；
- “编号冲突”。

错误提示必须指出具体问题，例如“编号只有 5 位”“标签包含 `/`”“编号 `010203` 已被两个文件使用”，避免只显示“文件名非法”。

## 11. 核心操作流程

### 11.1 新建文档

1. 用户选择一级和二级分类；
2. 软件推荐序号；
3. 用户填写标题和可选标签；
4. 软件展示完整目标文件名；
5. 提交前重新检查编号和路径冲突；
6. 创建 UTF-8 编码的空 `.md` 文件；
7. 刷新内存视图并选中新文档。

软件只创建空文件，不自动插入 Front Matter 或正文模板。模板能力属于后续扩展。

### 11.2 将已有文件纳入管理

1. 用户选择一个 `unmanaged` 文件；
2. 默认使用原文件名去除扩展名作为标题；
3. 用户选择分类、序号和标签；
4. 软件生成重命名预览；
5. 用户确认后执行安全重命名；
6. 文件内容保持逐字节不变。

### 11.3 修改分类、标签或标题

所有修改统一生成一个 `RenamePlan`：

```text
RenamePlan
├── sourceRelativePath
├── targetRelativePath
├── expectedSourceFingerprint
├── oldMetadata
├── newMetadata
├── errors[]
└── warnings[]
```

只有 `errors` 为空时才允许提交。`warnings` 需要用户确认，但不阻止提交。

### 11.4 重命名提交

提交时必须按以下顺序执行：

1. 再次确认源文件仍然存在；
2. 比较文件大小和修改时间等轻量指纹，确认没有被外部替换；
3. 再次检查目标路径不存在；
4. 检查区分大小写后的名称冲突；
5. 执行同一文件系统内的原子重命名；
6. 若仅修改名称大小写，则使用唯一临时文件名中转；
7. 更新内存视图；
8. 将本次操作加入当前会话的撤销栈；
9. 若任何一步失败，保留原文件并显示可操作的错误信息。

不得覆盖已有文件，也不得通过“复制后删除源文件”的方式模拟普通重命名。

### 11.5 撤销

第一阶段提供当前应用会话内的单步或多步重命名撤销：

- 撤销前重新检查原目标位置是否空闲；
- 若原名称已被占用，不执行撤销并说明原因；
- 应用关闭后无需保留撤销历史；
- 撤销记录存放在内存中，不写入工作区配置。

### 11.6 外部删除

第一阶段不在软件内提供永久删除按钮。文件被外部工具删除后，监听器应从界面移除对应项，并重新计算标签集合和编号冲突状态。

## 12. 链接风险处理

重命名 Markdown 文件可能使其他文档中的相对链接、Wiki Link 或外部引用失效。

第一阶段不修改任何 Markdown 正文，因此采用以下策略：

- 每次重命名前显示固定警告：“重命名可能使其他文档或外部工具中的链接失效”；
- 用户可以在工作区配置中关闭该警告；
- 软件不得声称链接已经被自动修复；
- 自动扫描和修改 Markdown 链接列为后续功能，启用时也必须提供修改预览。

## 13. 并发与外部同步场景

虽然软件不负责同步，但工作区可能位于同步目录中，因此需要采用乐观并发检查：

- 不长期锁定整个工作区；
- 生成预览和正式提交之间若源文件发生变化，则取消操作并要求重新加载；
- 目标文件突然出现时禁止覆盖；
- 同步工具产生的“冲突副本”视为普通新文件并重新扫描；
- 文件暂时不可用时显示错误，不自动删除记录对应的实际文件；
- 配置文件发生外部变化时重新加载并提示用户界面规则已经更新。

## 14. 技术方案

### 14.1 推荐技术栈

```text
Electron
├── Renderer：Vite + TypeScript + React
├── Preload：TypeScript + contextBridge
├── 本地核心：Node.js + TypeScript（Main Process）
├── 配置：JSON + 运行时 Schema 校验
├── 文件监听：跨平台文件系统监听器
└── Unicode 规范化：String.prototype.normalize('NFC')
```

选择 Electron + Node.js 的原因：

- 前端、IPC 数据结构和本地核心统一使用 TypeScript，降低实现和维护成本；
- Node.js 文件系统 API 足以承担目录扫描、配置管理、安全重命名和文件监听；
- LeafMark 第一阶段只处理文件名和文件元数据，不读取正文，Node.js 性能足以满足目标规模；
- Electron 的 Windows 和 macOS 构建、安装包和桌面集成方案成熟；
- Electron 安装包自带运行时，最终用户不需要单独安装 Node.js；
- 可以为 Windows 和 macOS 分别构建应用；
- React 界面、共享类型和核心规则能够在一个 TypeScript 工程中统一测试。

采用 Electron 的代价是安装体积、常驻内存和启动成本通常高于基于系统 WebView 的方案。本文中的“功能聚焦”指产品范围小、无账号、无数据库、无正文编辑和无后台服务，不将极小安装包或极低内存占用作为 MVP 的首要目标。

不得采用“Tauri + Node.js sidecar”作为默认方案。该组合仍需要 Rust/Tauri 构建链，同时引入额外进程、IPC 和多平台打包复杂度，不能实现彻底移除 Rust 的目标。

LeafMark 的工程命名统一如下：

| 项目 | 名称 |
| --- | --- |
| 产品显示名 | `LeafMark` |
| 代码仓库建议名 | `leafmark` |
| 可执行程序名 | `leafmark` |
| 工作区配置文件 | `.leafmark.json` |
| 前端包名建议 | `leafmark-ui` |
| 本地核心包名建议 | `leafmark-core` |
| Electron 主进程入口 | `src/main/index.ts` |
| Preload 入口 | `src/preload/index.ts` |

应用包标识符涉及发布主体和域名，应在正式发布前确定，不在本文中虚构固定域名。

### 14.2 模块划分

```text
src/
├── main/                       Electron Main Process
│   ├── index.ts                应用入口和窗口生命周期
│   ├── ipc/                    业务级 IPC Handler
│   ├── config/                 配置读取、校验和原子写入
│   ├── scanner/                目录扫描与忽略规则
│   ├── parser/                 文件名解析、规范化和校验
│   ├── allocator/              编号占用统计与推荐
│   ├── rename/                 预览、提交、大小写中转和撤销
│   └── watcher/                文件系统监听与防抖
├── preload/
│   └── index.ts                contextBridge 白名单接口
├── renderer/                   React Renderer
│   ├── components/             通用界面组件
│   ├── features/tree/          分类树
│   ├── features/list/          文档列表和筛选
│   ├── features/editor/        命名编辑与预览
│   ├── features/issues/        未管理、异常和冲突视图
│   ├── services/               类型化 IPC 客户端
│   └── stores/                 前端会话状态
└── shared/
    ├── model/                  共享数据结构
    ├── ipc-contracts/          IPC 请求、响应和事件类型
    └── error-codes/            稳定错误码
```

纯规则模块不得依赖 Electron 窗口对象或 React，以便使用普通单元测试直接验证解析、生成、编号分配和 RenamePlan。

### 14.3 进程职责

Main Process 是文件操作和规则校验的最终权威，负责：

- 路径规范化和安全检查；
- 读取配置；
- 扫描和解析；
- 编号冲突检查；
- 创建文件；
- 生成并提交重命名计划；
- 文件监听；
- 撤销执行。

Preload 只负责通过 `contextBridge` 暴露经过白名单限制的业务接口，例如选择工作区、请求扫描、生成重命名预览和提交重命名。Preload 不得把 `fs`、`path`、`ipcRenderer` 或任意命令执行能力直接暴露给 Renderer。

Renderer 负责：

- 展示分类树和文档列表；
- 收集用户输入；
- 即时展示 Main Process 返回的预览、错误和警告；
- 维护筛选条件和当前选择；
- 不直接访问 Node.js、Electron 或文件系统 API 修改工作区。

Renderer 可以做快速输入校验，但提交时必须由 Main Process 重新验证，不能把 Renderer 校验视为安全边界。

### 14.4 IPC 与窗口安全基线

BrowserWindow 必须采用以下安全基线：

- `nodeIntegration: false`；
- `contextIsolation: true`；
- `sandbox: true`；
- Renderer 只加载随应用打包的本地资源，不加载远程网页；
- 使用限制性 Content Security Policy；
- 禁止任意导航、新窗口和未经校验的外部链接；
- 每个 IPC Handler 都校验调用来源、请求结构、工作区边界和当前状态；
- IPC 只暴露业务级方法，不提供任意路径读写或通用文件操作接口。

建议的 Renderer 接口保持窄而稳定：

```ts
interface LeafMarkAPI {
  selectWorkspace(): Promise<WorkspaceSummary | null>;
  scanWorkspace(): Promise<ScanResult>;
  previewRename(input: RenameInput): Promise<RenamePlan>;
  commitRename(planId: string): Promise<RenameResult>;
  createDocument(input: CreateDocumentInput): Promise<CreateResult>;
  undoLastRename(): Promise<UndoResult>;
  rescan(): Promise<ScanResult>;
}
```

`commitRename` 应接收由 Main Process 生成和保存的短期 `planId`，而不是信任 Renderer 回传的任意源路径和目标路径。提交时仍需重新检查源文件指纹、目标占用和工作区边界。

## 15. 跨平台约束

实现过程中必须覆盖以下差异：

- 所有路径组合、规范化和相对路径判断使用 Node.js `path` API，不手工拼接分隔符；
- 所有来自 Renderer 的路径参数都必须在 Main Process 中执行 `resolve` 和工作区边界校验；
- 不假设路径分隔符一定是 `/`；
- 比较潜在冲突时考虑 Windows 和默认 macOS 文件系统通常不区分大小写；
- 处理 macOS 文件名可能出现的 Unicode 分解形式，并统一为 NFC；
- 正确处理仅改变大小写的重命名；
- 不生成 Windows 禁止字符和尾部句点、空格；
- 忽略规则使用统一的 `/` 作为配置语法分隔符，再由后端适配系统路径；
- Windows 和 macOS 分别构建、测试和发布；
- 代码签名、公证和自动更新不属于首个 MVP，但发布前必须单独规划。

Linux 可以作为后续支持平台。核心代码不得主动依赖只能在 Windows 或 macOS 使用的专有接口。

## 16. 隐私与安全

- 软件默认不联网；
- 不上传文件名、目录结构或文档内容；
- 只访问用户明确选择的工作区；
- 第一阶段不读取 Markdown 正文；
- 不执行 Markdown 中的脚本或命令；
- Renderer 禁止启用 Node.js integration，并保持 context isolation 和 sandbox；
- 只有 Main Process 可以执行文件系统变更，Preload 只暴露经过白名单限制的业务接口；
- IPC Handler 必须校验来源、参数 Schema、工作区边界和操作时状态；
- 不向 Renderer 暴露任意文件读取、写入、重命名、Shell 或进程执行能力；
- 所有覆盖风险必须转化为显式冲突，禁止静默覆盖；
- 错误日志应避免记录用户的完整 Markdown 正文；
- 遥测和自动更新若后续加入，必须独立征得用户同意。

## 17. 性能目标

首个版本以个人文档库为目标：

- 5,000 个 Markdown 文件的初次扫描目标为 2 秒内完成，具体结果以常见本地 SSD 为准；
- 普通重命名在无冲突时应在 200 ms 内反映到界面；
- 文件监听事件不得导致界面反复全量闪烁；
- 扫描在后台执行，超过 300 ms 时显示进度或忙碌状态；
- 大目录中应支持取消扫描或切换工作区。

性能目标不是以牺牲冲突检查和数据安全为代价的硬性实时保证。

- 配置原子写入失败时保留旧文件；
- 配置中非法分类代码和非法固定标签被准确报告。

### 18.5 平台验收

至少在以下环境执行核心流程：

- Windows 11，NTFS；
- macOS 当前支持版本，APFS；
- 包含中文、英文、空格和长路径的工作区；
- 位于常见同步目录中的工作区，但不要求软件控制同步过程。

## 20. MVP 验收标准

满足以下条件时，第一阶段可以视为完成：

1. 用户可以在 Windows 和 macOS 分别打开同一个命名规则的工作区，得到一致的编号、标签和状态解析结果。
2. 不启动任何 Markdown 编辑器，也可以完成创建、纳入管理和规范化重命名。
3. 修改分类后，六位编号随分类位置正确变化。
4. 软件不会覆盖同名文件，不会在失败时删除源文件，也不会修改 Markdown 正文。
5. 两个文件编号相同时，软件能够发现并阻止继续产生冲突。
6. 外部创建、删除或重命名文件后，界面能够在合理时间内更新。
7. 删除应用的缓存或重新启动后，能够仅凭目录、文件名和配置文件恢复完整管理视图。
8. 删除 `.leafmark.json` 后，Markdown 文件仍然可读，编号、标签和标题仍可从文件名恢复。
9. 配置文件中不存在文档索引、绝对路径或内部文档 ID。
10. 工具不提供正文编辑能力，也不要求用户采用特定 Markdown 编辑器。

## 22. 对实现 Agent 的约束

实现 Agent 应遵循以下原则：

1. 先实现和测试纯规则核心，再连接图形界面。
2. 不得用数据库替代目录扫描。
3. 不得把文件列表或文档元数据写入配置文件。
4. 不得为了方便而加入 Markdown 编辑器、云同步或账号系统。
5. 文件名解析、目标生成和最终提交必须使用同一套后端规则。
6. 任何可能覆盖文件的情况都必须安全失败。
7. 所有文件系统写操作只能发生在 Electron Main Process；Renderer 不得直接访问 Node.js 或文件系统。
8. Preload 只能暴露业务级白名单接口，不得直接暴露 `ipcRenderer`、`fs`、`path`、Shell 或通用命令执行能力。
9. Main Process 必须验证每个 IPC 请求，不能信任 Renderer 提供的绝对路径、目标文件名或旧校验结果。
10. 解析、校验、编号分配和 RenamePlan 应实现为不依赖 Electron 的纯 TypeScript 模块，并分别进行单元测试。
11. 优先使用 Node.js 标准库，新增第三方依赖时应说明用途，避免为小功能引入大型依赖链。
12. 不明确的交互可以调整，但不得改变本文“已确定的设计决策”。
13. 若实现发现文件系统限制与本文冲突，应先报告具体平台、复现条件和数据风险，再修改设计。
14. 每个阶段都应提交可运行结果和对应测试，不应先搭建全部界面再补文件安全逻辑。
